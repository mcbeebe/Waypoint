Waypoint Implementation Plan

One consolidated plan covering every gap in the audit plus all of PRD v2.0 (F1–F15). Eight phases, ordered by leverage: unlock what's already built, then port the proven GAS features, then build what's never existed. Each phase ends at a shippable state with an explicit review gate.

Sequencing logic

Phases 0–1 are strictly first: 0 multiplies the value of everything after it, and 1 is the differentiator users feel immediately. 2→3→4 build on each other (documents feed letters; letters feed follow-ups) but 3 and 4 can start while 2's tail finishes. 5 and 6 are independent of each other and could swap based on what traction demands — insurance pain (5) vs. community growth (6). 7 threads through everything and should claim ~20% of each week rather than waiting until the end.

UX plan — standards & practices

How every workstream above gets built: a design contract applied to each phase, reviewed at each gate. Grounded in WCAG 2.2 AA, Nielsen's heuristics, Apple HIG / Material patterns, and the trauma-informed plain-language standards this audience deserves.

UX 1

Design system before screens

theme.ts tokens (navy/teal/coral/sage, spacing, radii) become the single source of truth, extended with semantic roles (success/warning/danger/info), a fixed type scale, and an 8-pt spacing grid. A documented component kit — buttons, cards, chips, list rows, sheets, form fields, banners — is built once in Phase 0–1 and every later screen composes from it. The 16 WayPoint 2.0 HTML mockups (01_Onboarding … 16_ProviderPortal) are the reference designs: new screens match their layout intent before inventing anything.

UX 2

Navigation & information architecture

Standard tab + stack pattern (Phase 0): five tabs, detail screens push with a titled header and back affordance, modals only for interruptions (confirmations, pickers). On web, React Navigation's linking config gives every screen a real URL — browser back/forward works, and any screen can be shared or bookmarked. Maximum three taps from Home to any core task. One primary action per screen.

UX 3

Accessibility — WCAG 2.2 AA

4.5:1 text contrast (validated against both themes), 44-pt minimum touch targets, visible focus states, screen-reader labels and state announcements on every interactive element (wire the existing lib/accessibility.ts helpers), reduced-motion respected, text scaling to 200% without breakage. Audited per-gate with axe/Lighthouse on the web build — not saved for Phase 7; 7.5 is the sweep that certifies it.

UX 4

Content design for stressed parents

The GAS MVP's voice — "a friend who happens to be a disability rights attorney" — becomes a written style guide: 6th–8th-grade reading level, empathy before instruction, jargon always paired with a tap-to-explain (Learn More system, 1.5), progress celebrated, deadlines framed as support not threat ("You have until March 12 — plenty of time" vs. "DEADLINE"). Errors say what happened and what to do next; nothing dead-ends. Spanish is written by translation review, not machine passthrough.

UX 5

State completeness — the four states rule

No screen ships without all four states designed: loading (skeletons, not spinners, for lists), empty (the shared EmptyState component with a next-step CTA — currently orphaned and shadowed by a local copy), error (retry + explanation), and offline (cached data visible, actions queued with visible "will sync" status via 7.2). Optimistic updates with undo where the pattern already exists (actions, expenses).

UX 6

Forms, trust & PWA mechanics

Forms: single column, inline validation on blur, input never lost on navigation or crash (draft autosave), sensible keyboards and autofill hints. Trust: explicit consent screens before Google or Epic connections stating exactly what's read and why; privacy, data export, and delete-account visible in Settings, not buried. PWA: installable with a correct manifest, offline app shell, <100 ms tap feedback, safe-area insets, and the existing per-build cache-busting service worker kept honest.

UX 7

Validation loop

Each phase gate includes a usability pass: persona walkthroughs (the PRD's four personas — first-diagnosis Maria, veteran Sarah, transition David, multi-system Priya) against the gate's scenario, plus 3–5 real parent sessions when available. Analytics funnels (7.3) instrument the same scenarios so post-launch data confirms what testing suggested. Findings feed the next phase's backlog — the plan bends to evidence.
